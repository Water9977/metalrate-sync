## What this is

**MetalRate Sync** — a Shopify app that automatically updates product prices based on live gold, silver, platinum and palladium rates, so jewelry and bullion sellers never have to manually reprice their catalog when the market moves. Core wedge: bulk update reliability at 10k+ SKU scale plus preview-before-commit.

App name: **MetalRate Sync** (chosen for ASO keyword coverage: metal + rate + sync; doesn't lock us out of jewelry segment the way "Bullion" branding would).

## How it works (plain English)

A merchant creates a **formula**: pick a metal (gold/silver/platinum/palladium), a purity (22K, 18K, sterling, etc.), and how they want to add making charges, wastage %, markup, and tax on top of the raw metal value. That formula is just math — it doesn't touch anything by itself.

Then they go to a **product variant** and tell the app two things: how much it weighs in grams, and which formula to use. Now that variant is "tracked."

Every time the merchant opens **Preview & Sync**, the app fetches today's live gold/silver/platinum/palladium rate, runs every tracked variant through its assigned formula, and shows a table: current price → what the new price would be → % change. **Nothing changes in the store yet at this point** — it's a dry run so the merchant can sanity-check before committing (this is the one thing multiple competitors don't do, see competition-analysis.md).

When they click **Apply**, the app pushes the new prices to Shopify in safe batches and writes down exactly what happened to every single variant — updated, skipped, or failed and why — in **History**. That audit trail is the actual product: the wedge against Gold Feed Inc. (Chris's current $40/mo app) isn't cleverer math, it's that this one doesn't quietly break and go silent when something goes wrong.

## Known issue found and fixed: React Router server/client split

Hit this live: `METAL_LABELS`/`SUPPORTED_METALS`/`PURITY_PRESETS` were originally defined inside `.server.ts` service files and imported directly into route components for rendering. React Router strips `.server.ts` files down to just `loader`/`action` when bundling for the browser — pulling a plain constant out of one for JSX breaks the split, and the failure mode is nasty: Vite's error overlay is a full-page modal that blocks the *entire* app regardless of which tab is open, so it looked like every page was broken when only one import was wrong.

**Fix**: moved `METAL_LABELS`, `SUPPORTED_METALS`, `PURITY_PRESETS`, and a new `METAL_TONE` color map into [app/constants.ts](metalrate-sync/app/constants.ts) — a plain file with no `.server` suffix, safe to import from both loaders and JSX. Rule going forward: **anything a route renders directly must not live in a `.server.ts` file**, only functions called inside `loader`/`action` can.

## Known constraint: MetalPriceAPI free tier

Free plan = ~100 requests/month, **per merchant's own API key** (each shop brings its own key in Settings — not shared across installs). At the original 15-minute cache default this blows the monthly quota in about a day. Fixed: default `rateTtlMinutes` raised to 480 (8h) for all new installs, and Settings now explains the tradeoff. Existing shops (including the test store) should bump this manually in Settings if they're on the free tier. Roadmap item: bundle a paid rate-provider key for paying customers so nobody has to think about this themselves.

## Pricing volatility, rounding, and the "ugly $3 move" question (2026-07-16)

Real question that came up: a $220 22K gold chain, gold ticks a little, does the price now show $217 or $223 and look broken? Researched this properly instead of guessing.

**Real volatility numbers (mid-2026, sourced from Barchart ADR/ATR and CBOE GVZ):** on $200 of gold content, expect roughly **$3-8 of movement on a normal day, $10-15+ on a volatile one**. Silver and platinum move proportionally more (silver's daily range runs ~2x gold's). So the "ugly $3 swap" the question describes isn't a bug or an edge case — it's the realistic, common outcome of tracking spot price honestly. 2026 has been an unusually volatile year for metals generally (gold spiked over $5,100/oz in January, crashed, sits around $4,050 now), so if anything today's swings are a bit above long-run normal, not below it.

**Built the fix — but the research changed which way to point the *default*.** Added three new formula settings: `roundingStep` (round to nearest 0/1/5/10/25/50/100), `endsIn99` (charm pricing), and `minChangeAmount` (skip repricing if the move is smaller than this). See [pricing.server.ts](metalrate-sync/app/services/pricing.server.ts).

Then visited real stores to check the actual assumption. Full findings: [research/pricing-volatility-and-rounding.md](research/pricing-volatility-and-rounding.md).
- **Bullion dealers (13 sites checked: APMEX, JM Bullion, SD Bullion, Kitco, Liquid Bullion, etc.) are unanimous: exact-cent pricing, everywhere, no exceptions.** None round. Most run a live ticker. This confirms the app's default (roundingStep 0, minChangeAmount 0 = exact tracking) is correct for that segment, don't touch it.
- **Real by-weight jewelry sellers (BlueStone, Melorra, PNG Jewellers, CRM Jewelers, Orionz — the actual target segment, not generic DTC brands) mostly do NOT round either.** BlueStone and Melorra show fully arbitrary rupee amounts with no smoothing at all. CRM Jewelers rounds only to the nearest whole dollar, never to a step. They build trust through a visible rate ticker or an itemized price breakup instead of a clean-looking number. Only **fixed-price, non-gold-linked** brands (Mejuri, Catbird, Ana Luisa — prices set by hand, not tied to spot) land on clean $5/$10 steps, and they can do that precisely because their price isn't chasing a moving target.

**So the honest takeaway: rounding/threshold is a real, useful, and differentiated feature (nobody else in the competitive set has it), but it should ship as an opt-in a jeweler reaches for if they want it, not a default the app pushes on everyone.** Default stays exact/always-update to match what real by-weight sellers actually do today. If a merchant explicitly wants clean numbers (a valid ask, just not the market norm), roundingStep 5 or 10 plus minChangeAmount ~5 gets there.

## Two real bugs found during first click-through, both fixed (2026-07-16)

**Navigation was broken app-wide.** Every primary-action button and every in-content link was built as `<Link to="..."><s-button slot="primary-action">...</s-button></Link>`. Two separate problems in that one pattern: (1) Polaris slots only project from a *direct child* of `s-page` — wrapping the button in a `<Link>` (which renders an `<a>`) means the button itself is no longer a direct child, so it never gets slotted and the click does nothing; (2) `<Link><s-link>...</s-link></Link>` is a nested anchor, also broken. Confirmed against Shopify's own official docs examples, which use `useNavigate()` + `onClick` for primary actions and plain `<s-link href="...">` for in-content links — no `Link` wrapper at all. Rewrote every navigation call site across all 6 route files this way. Also fixed the CSV download button, which was a plain `<a href>` that would've opened a new browser tab outside the embedded session and failed authentication — now does an authenticated `fetch()` + client-side blob download instead.

**Formulas couldn't be edited, only deleted.** Two compounding bugs: no Edit button existed in the table at all, and even the save action's `<input type="hidden" name="id">` was missing from the form — so even a hypothetical edit submission would've always silently created a new formula instead of updating, since the action branches on whether an `id` was present. Added an Edit button per row, wired it to pre-fill the modal from the selected formula (remounting the form via `key={formula.id}` so every field's default value reflects the right formula rather than relying on custom elements to sync a changed prop), and added the missing hidden `id` field. Editing a formula's Active switch is how activate/deactivate works — no separate control needed.

## MetalPriceAPI investigated — pricing math confirmed correct

A merchant test (50g, 22K, zero markup formula) showed $5,867.99 while a casual web search suggested "$6000+." Investigated properly rather than assuming either the app or the API was wrong:

- Live-tested the actual API response: gold was $3,984.54/oz at that moment. Working the formula by hand (50 × 0.916 × $3,984.54/31.1034768 = $5,867.25, then the formula's own ".99" charm-pricing rounding → $5,867.99) matches the app's output exactly.
- Confirmed the app's `1/rate` inversion logic is correct by comparing against the API's own `USDXAU` field, which is the pre-inverted equivalent — both agree to the cent.
- The ">$6000" figure was almost certainly a **retail price** (includes a dealer's markup), not spot — apples to oranges against a formula explicitly named "no taxes or making charges." Also: different dealers' spot quotes routinely differ 1-2% from each other just from feed timing (matches what the pricing-volatility research already found).

**Correction to the above (2026-07-18): the claim "MetalPriceAPI has no city/country selection" was wrong** — caught it based on a docs page the user pointed at, not something found unprompted, worth being straight about that. The `/v1/documentation` page genuinely doesn't describe it, but `/v1/symbols`, checked live against the real API, lists **56 India city-specific gold/silver symbols** (`XAU-MUMB`, `XAG-KOLK`, etc. — 34 cities have gold data, 18 of those also have silver; platinum/palladium have no city data at all). Confirmed live that requesting one actually works, gated behind a paid plan (`XAU-MUMB query requires a paid plan` — free tier blocked, exact required tier not documented anywhere public).

**Built it.** `ShopSettings.rateCity` (nullable, defaults to global/off), a full city list with per-metal availability in [constants.ts](metalrate-sync/app/constants.ts) (`INDIA_RATE_CITIES`), request-symbol logic in [rates.server.ts](metalrate-sync/app/services/rates.server.ts) that swaps in the city-suffixed symbol only for gold/silver and only when the selected city actually has that metal's data, always falling back to the global symbol otherwise. A Settings dropdown exposes it, labeled clearly that it needs a paid plan. Verified with 5 mocked-fetch assertions: correct symbol selection for a city with both metals, correct fallback for a gold-only city, correct unchanged behavior with no city set, correct rate computation, correct storage under the plain metal code regardless of which symbol was actually requested. Not live-verified against a real paid response (nobody has one active) — logic is proven, the real paid-tier response shape is assumed to match the free-tier shape (same `rates` object, just keyed by the city symbol instead of erroring), which is the standard, low-risk assumption for this API's endpoint design.

The MCX/IBJA-specific roadmap item (India domestic rates including import duty + GST, structurally different from international spot) is still separate and still open — these are city-level *international* gold/silver quotes from the same MetalPriceAPI feed, not the same thing as MCX/IBJA board rates.

## Production rate-fetch decision (2026-07-18, from user)

When this ships to real customers: **one app-owned MetalPriceAPI key** (not per-merchant BYO keys), prices updated **twice a day** on a fixed schedule. The per-merchant key field in Settings is a development convenience and gets removed/hidden before launch. Cost math: rates are global, so with central caching, 2 fetches/day serves every merchant on the base tier; each extra (city × currency) combo adds 2 calls/day. Even 100 merchants across 10 combos ≈ 600 calls/month → MetalPriceAPI's $12/mo Basic plan (10k req) covers it with huge headroom. API cost is effectively zero per merchant; price on value, not cost.

## Formula edit — root cause #2, actually fixed this time (2026-07-18)

Edit button existed, was wired to `openEditFormula`, but clicking it still did nothing. Cause: `showModal()` called `document.getElementById("formula-modal")?.show?.()` — **`.show()` isn't a real method on `s-modal`.** Confirmed against Shopify's own docs: the actual API is `shopify.modal.show(id)` / `shopify.modal.hide(id)` via the App Bridge object (already available in the component from `useAppBridge()`). Optional chaining (`?.show?.()`) silently swallowed the call to a method that never existed — no error, no console warning, just nothing happening, which is exactly why it was easy to miss the first time. Same wrong pattern was used for closing the modal after a successful save; fixed both call sites to use `shopify.modal.show/hide("formula-modal")`. Grepped the rest of the codebase for the same `getElementById(...).show/hide` pattern — this was the only place it existed.

## Code audit fix pass (2026-07-18, evening) — all 18 items closed

Worked through every open item from the audit one at a time: fix, typecheck, next. Full project typecheck + production build run clean at the end. No git operations until this pass was complete, per instruction.

**HIGH:**
- **H3 (price drift) fixed first**, since it's the most brand-damaging (undermines the "approve before it changes" pitch). [sync.server.ts](metalrate-sync/app/services/sync.server.ts): split the batched-apply logic out of `executeSync` into a shared internal `runBatchedApply`, and added a new exported `applyPreviewedRows(admin, shop, rows, rates)` that applies exactly the rows/rates the merchant was shown — no recompute. [app.sync.tsx](metalrate-sync/app/routes/app.sync.tsx)'s Apply action now round-trips the previewed rows+rates as JSON and calls the new function, with a server-side staleness check (rejects and asks for a refresh if the rates are older than the configured TTL). Scheduled syncs still call `executeSync`, which recomputes fresh — correct for them, there's no human approval to honor.
- **H2 (scheduler + idle tokens) fixed second.** Read the actual framework source (`@shopify/shopify-app-react-router`'s `ensureOfflineTokenIsNotExpired` → `refreshToken`) rather than guessing: confirmed `unauthenticated.admin()` **does** auto-refresh via the stored refresh token, so a shop that's merely been idle recovers on its own — that part of H2 wasn't actually broken. What's genuinely unhandled: a refresh that fails *permanently* (uninstalled shop, revoked token) would retry every minute forever. Added a circuit breaker: `ShopSettings.scheduleFailureCount` + `lastScheduleError` (new migration `20260719050000_scheduler_circuit_breaker`), scheduling auto-disables after 5 consecutive failures, and [app.settings.tsx](metalrate-sync/app/routes/app.settings.tsx) shows the merchant why if it happened.
- **H1 (rate-cache quota burn) fixed third.** [rates.server.ts](metalrate-sync/app/services/rates.server.ts) `getRates`: the old freshness check required **all 4 metals individually fresh**, so one metal the provider chronically can't supply (partial outage, unsupported city+metal combo) made the gate permanently false — refetching from the live API on every single page load, forever. Changed to gate on the **most recent** successful update instead of every-metal-individually — a normal partial response (3 of 4 metals) still counts as "just refreshed" and throttles the next call to once per TTL like a full response would. Also: a metal missing from a given provider response now falls back to its last cached value instead of vanishing from the result.

**MEDIUM:**
- **M1**: [app.settings.tsx](metalrate-sync/app/routes/app.settings.tsx) — saving Settings while on Manual/Demo no longer wipes the stored India city; the field is only written when the submitted provider is actually `metalpriceapi`.
- **M2**: [sync.server.ts](metalrate-sync/app/services/sync.server.ts) — `skippedCount` now covers every non-actionable row (including `missing_data`, which used to be excluded), so `updated + skipped + failed` always reconciles against `totalItems`.
- **M3**: [app.products.tsx](metalrate-sync/app/routes/app.products.tsx) — the weight field + unit dropdown are now controlled React state; switching units converts the displayed number so it always matches what's selected, closing the 11.66x tola-misread trap.

## Deployed to Railway — live (2026-07-18)

Went from "runs on a dev tunnel" to a real persistent URL in one session. Full chain, in the order each thing was actually hit:

1. **Chose Postgres over SQLite+volume** (user decision) to fix H4 properly rather than patch around it — matches "we want our app the best."

6. **Third deploy succeeded** (build + Postgres migration both clean), but the container crashed on boot: `SHOPIFY_API_SECRET` wasn't set. Expected — that's the one variable that has to be the user's own action, never something I touch.
7. **`shopify app deploy` shipped a live app version still pointing at `application_url = "https://example.com"`** — the placeholder was never updated for production. Fixed `shopify.app.toml`'s `application_url` and `auth.redirect_urls` to the real Railway domain (`/auth/callback`, matching `authPathPrefix: "/auth"` in `shopify.server.ts`), redeployed the config.
8. **Key/secret mixup**: user pasted what looked like the secret into the `SHOPIFY_API_KEY` field (overwriting the correct public client ID) instead of creating a new `SHOPIFY_API_SECRET` variable. Caught it from the value's shape (`shpss_...` prefix, not a bare client-ID-looking string), walked through the fix without ever displaying the actual secret value.
9. **Confirmed live**: `curl` returned HTTP 200 with real rendered HTML from the Railway domain. App installed and exercised successfully on the real dev store against the deployed URL, not localhost.

**Known gotcha going forward**: `automatically_update_urls_on_dev = true` in `shopify.app.toml` means `application_url` silently flips back to whatever local dev tunnel is active every time `npm run dev` runs. Check this file before any future `shopify app deploy` if there's been a local dev session in between — this is exactly how step 7 above happened.

## Codebase map (metalrate-sync/)

- **Template**: official `shopify-app-template-react-router` (React Router 7, the current Shopify recommendation; Remix template is legacy). Embedded app, App Bridge v4, **Polaris web components** (`s-*` tags, globally registered, no imports — this is the current standard, NOT old @shopify/polaris React).
- **DB**: Prisma + SQLite (dev). Models beyond template's Session:
  - `ShopSettings` — rate provider (mock | metalpriceapi | manual), API key, base currency, cache TTL, schedule config, `lastScheduledSyncAt` (set by the scheduler, not the user), `scheduleFailureCount` + `lastScheduleError` (H2 circuit breaker, added 2026-07-18)
  - `MetalRateCache` — cached spot rates per shop/metal/currency
  - `ManualRate` — merchant-entered board rates (per gram)
  - `PricingFormula` — metal, purity factor, making charge (flat/perGram/percent), wastage %, markup, tax %, `roundingStep` + `endsIn99` + `minChangeAmount` (replaced the old 3-mode `rounding` string, see the "ugly $3 move" section above), stop-loss floor
  - `VariantConfig` — per-variant: weight grams, purity override, formula assignment, last synced price
  - `SyncRun` / `SyncRunItem` — full per-variant audit trail of every sync (the trust feature)
  - `BulkCatalogJob` — tracks one in-flight/last Bulk Operations catalog fetch per shop, so a retry within the polling window reuses the running job instead of restarting it on Shopify's side
- **Services** (`app/services/`):
  - `rates.server.ts` — provider abstraction. Mock (works out of box on dev store), MetalPriceAPI (live), Manual. Caches with TTL, falls back to stale cache if provider is down.
  - `pricing.server.ts` — pure formula engine: weight × purity × rate + wastage + making + markup + tax, step rounding + charm pricing, stop-loss detection, and `isChangeBelowThreshold` (the min-change guard). Karat presets (24K/22K/18K/14K/10K/925).
  - `sync.server.ts` — THE wedge. Preview builder (diff of current vs computed price per variant) + sync executor: groups by product, chunks ≤250 variants/call (`productVariantsBulkUpdate` API limit), `allowPartialUpdates: true`, retries with exponential backoff on throttle, records per-variant outcome in SyncRunItem, unconfirmed variants treated as failed (nothing silently disappears).
  - `catalog.server.ts` — SKU-keyed catalog fetch. Fast paginated GraphQL under 2,000 variants; automatically escalates to Shopify's **Bulk Operations API** beyond that (start → poll with a bounded 45s budget → download/parse JSONL), with job state persisted so a retry doesn't restart it. Falls back to a partial fast-path result (marked truncated) if the bulk mutation itself fails, rather than throwing.
  - `csv.server.ts` — hand-rolled CSV parse/write (no dependency; handles quoted fields, embedded commas/newlines). Import expects a `sku` column, optional weight column in grams/tola/vori/troy oz/pennyweight, and `formula`.
  - `import.server.ts` — the actual bulk-import logic (extracted from the route so it's directly testable): parse → match by SKU → look up formula by name → upsert config → report what didn't match.
  - `scheduler.server.ts` — in-process scheduler, ticks every minute via `setInterval`, guarded against duplicate starts (HMR-safe) and overlapping runs per shop. Uses Shopify's official `unauthenticated.admin(shop)` background-job pattern.
  - `scheduling.server.ts` — the pure "is a sync due yet" timing decision, deliberately dependency-free so it's testable without pulling in the live Shopify app context.
- **Routes** (`app/routes/`, Polaris web components):
  - `app._index.tsx` — Dashboard: live rate cards, setup guide (4 steps), last sync summary, at-a-glance stats
  - `app.products.tsx` — product/variant list via Admin GraphQL, per-variant weight (with unit picker) + formula assignment inline, "Bulk import" button
  - `app.products_.import.tsx` — **the wedge feature.** Download current catalog as CSV → edit in Excel/Sheets → upload → matches by SKU, sets weight/formula for every matched row in one pass, reports SKUs not found and unknown formula names instead of failing silently. Reuses the existing Preview & Sync flow for the actual pricing — import only writes config, it doesn't touch prices itself. 10MB upload cap, duplicate-SKU-safe (see M5 above).
  - `app.products_.export-csv.tsx` — resource route (no UI), streams the current catalog + existing config as a downloadable CSV template (renamed from the dotted form 2026-07-18, see L5 above)
  - `app.formulas.tsx` — formula list + create modal (karat presets, making charge, wastage, markup, tax, step rounding, charm pricing, minimum-change threshold, stop-loss)
  - `app.sync.tsx` — Preview & Sync: full diff table (current/new/% change/status), stop-loss + missing-data banners, apply button
  - `app.history.tsx` — run list + per-variant drill-down with rate snapshot per run
  - `app.settings.tsx` — provider/API key/currency/cache TTL/schedule, manual rate entry
  - `webhooks.compliance.tsx` — mandatory GDPR trio (customers/data_request, customers/redact, shop/redact); app stores no customer data, shop/redact wipes all shop rows
  - Template's `webhooks.app.uninstalled.tsx` + `webhooks.app.scopes_update.tsx` kept as-is
- **Config**: `shopify.app.toml` — scopes `write_products`, webhook API version 2026-10, compliance webhooks registered. App API version: October25 (template default).

## Deliberate design decisions

- **Variant config lives in app DB, not metafields (for now).** Simpler MVP; metafield sync + CSV/Matrixify import comes later (import reliability is Chris's pain — CSV import is a fast follow, not in base).
- **Rate providers behind an interface** — mock provider default so the app fully works on a dev store with zero external accounts. MetalPriceAPI chosen as first real provider (same vendor competitor Metal Updater uses; free tier available). IBJA (India) provider is a later add.
- **Preview-before-commit is default flow, not optional** — closes Metal Updater's admitted "Coming Soon" gap, matches JewelSync/Pricify, builds the trust the category lacks.
- **Scheduler is real (in-process `setInterval`), but only works on a persistent host** — chosen deliberately over building a full job-queue system before there's a hosting decision or real usage to justify one. Settings page says this explicitly. If/when the app moves to serverless hosting, this needs replacing with a real queue.
- **Every sync writes a full audit trail** — differentiation vs Gold Feed's "pricing inaccuracies" reputation; merchants can see exactly what changed, when, at what rate.
- **No permanent automated test suite (yet)** — instead, every new service this session was verified with a throwaway `tsx` script using a mocked Shopify admin client against the real (isolated, cleaned-up) local database, then deleted. Proves real logic without ever needing a live session or touching a secret. Documented as the pattern to follow in [metalrate-sync/README.md](metalrate-sync/README.md).
